## 2. Architecture in one page

- **Value**: `readonly struct LuaValue { LuaValueType Type (byte); double value; object? referenceValue; }` with `[StructLayout(LayoutKind.Auto)]` [C] [LC/src/Lua/LuaValue.cs#L23-L37](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaValue.cs#L23-L37). It is 24 bytes on x64 (8-byte ref + 8-byte double + 1-byte tag padded to 8) [U: layout arithmetic, not measured]. Numbers and booleans are stored inline in `value`; strings are .NET `string`; tables, functions, threads and userdata are in `referenceValue`. Lua 5.2 semantics: only doubles, the same as MoonSharp. Arithmetic, loads and moves never allocate.
- **VM**: a real Lua 5.2 register VM. Instructions are 32-bit `uint`s in the standard 5.2 encoding (6-bit op, 8-bit A, 9-bit B and C with an RK constant bit, 18-bit Bx) [C] [LC/src/Lua/Runtime/Instruction.cs#L89-L139](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/Instruction.cs#L89-L139), with the 40 opcodes of `lopcodes.h` [LC/src/Lua/Runtime/OpCode.cs#L3-L62](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/OpCode.cs#L3-L62). The compiler is go-lua's single-pass code generator, which also produces register allocation and RK operands.
- **Dispatch**: one `while(true)` loop with a dense `switch (opCode)` (the JIT builds a jump table) inside `MoveNext` [C] [LC/src/Lua/Runtime/LuaVirtualMachine.cs#L385-L1110](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L385-L1110). Lua-to-Lua calls, returns and Lua `__index` functions do not recurse in C#: they push a frame and `goto Restart` (L1472-L1477, L951-L959, L2030-L2036).
- **Stack**: one growable `LuaValue[]` per thread (`LuaStack`), registers addressed as `frameBase + A` [C] [LC/src/Lua/Runtime/LuaStack.cs#L10-L191](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaStack.cs#L10-L191). Frames are `record struct CallStackFrame` values (Base, ReturnBase, Function, VariableArgumentCount, CallerInstructionIndex, Flags, Version) kept in a `FastStackCore<CallStackFrame>` array, so a call allocates nothing [C] [LC/src/Lua/Runtime/CallStackFrame.cs#L5-L18](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/CallStackFrame.cs#L5-L18).
- **Upvalues**: classic Lua open/closed upvalues. `UpValue` either points at a register index on its thread's stack (open) or holds its own `LuaValue` (closed) [C] [LC/src/Lua/Runtime/UpValue.cs#L5-L76](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/UpValue.cs#L5-L76). Open upvalues are found by a linear scan of a per-thread list and closed on `RETURN` / `JMP A>0` [C] [LC/src/Lua/LuaState.cs#L724-L751](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaState.cs#L724-L751).
- **Tables**: an array part (`LuaValue[]`, 1-based keys, power-of-two growth, migration of hash keys on growth, a cached "known non-nil prefix" for `#`) plus `LuaValueDictionary`, a struct-entry chained hash map derived from the BCL `Dictionary` [C] [LC/src/Lua/LuaTable.cs#L7-L103](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaTable.cs#L7-L103), [LC/src/Lua/Internal/LuaValueDictionary.cs#L102-L286](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/LuaValueDictionary.cs#L102-L286).
- **Host functions**: `LuaFunction` wraps `Func<LuaFunctionExecutionContext, CancellationToken, ValueTask<int>>`. Arguments are a span view on the VM stack and results are written back to the stack: no argument list and no result tuple allocation [C] [LC/src/Lua/LuaFunctionExecutionContext.cs#L8-L196](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaFunctionExecutionContext.cs#L8-L196).
- **Async everywhere**: every execution path returns `ValueTask<int>`. Synchronous completion is the fast path; when a host function really suspends, the VM sets a `PostOperation` and returns to an async driver (`ExecuteClosureAsyncImpl`) that awaits and then resumes the loop [C] [LC/src/Lua/Runtime/LuaVirtualMachine.cs#L272-L332](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L272-L332). Coroutines are built on `ManualResetValueTaskSourceCore` [C] [LC/src/Lua/Internal/CoroutineCore.cs#L8-L293](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/CoroutineCore.cs#L8-L293).
- **CLR interop**: no reflection binding. Host types opt in with `[LuaObject]` on a `partial`, non-nested type; a Roslyn incremental source generator emits `ILuaUserData` plus `__index`/`__newindex`/metamethod `LuaFunction`s [C] [LC/src/Lua.SourceGenerator/LuaObjectGenerator.Emit.cs#L100-L291](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua.SourceGenerator/LuaObjectGenerator.Emit.cs#L100-L291).
- **GC**: no own collector, no `__gc`, no weak tables (`__mode`): a grep for `__gc`, `__mode`, `WeakReference` and `ConditionalWeakTable` under `src/Lua` finds nothing [C]. MoonSharp has neither feature either, so this is not a regression for us.
- **Conformance**: the official Lua 5.2 test files run in CI (code, goto, constructs, locals, literals, pm, sort, files, closure, errors, events, vararg, nextvar, math, bitwise, strings, coroutine, db, verybig; `calls.lua` is disabled because `string.dump` and reader-function `load` are not implemented) [C] [LC/tests/Lua.Tests/LuaTests.cs#L60-L80](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/tests/Lua.Tests/LuaTests.cs#L60-L80).

## 4. Selected implementation details worth copying (as ideas)

1. **Stack top bookkeeping.** `LuaStack.NotifyTop`/`GetWithNotifyTop` raises `top` monotonically, and `PopUntil` clears the abandoned slots so the GC can collect what they referenced (L52-L114). MoonSharp's `FastStack` should also clear popped slots once values are structs that hold references.
2. **The table "known prefix" cache.** `knownArrayPrefixLength` is a lower bound on the non-nil prefix, so `#t` and appends do not rescan. It is invalidated when a writable span or ref is handed out (`hasWritableArrayReferences`) [C] [LC/src/Lua/LuaTable.cs#L20-L26, L107-L132](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaTable.cs#L20-L132). Commit [606696b3](https://github.com/nuskey8/Lua-CSharp/commit/606696b3c0b41b72f52f75eb75bc2eb08e8be1d3) records `table.insert` x8192 going from 28.3 ms to 2.0 ms [S: commit message].
3. **Array-part growth rule.** A write goes to the array if `0 < index <= max(array.Length*2, 8)`; otherwise, or if `index - array.Length > 4096`, it goes to the hash. On growth, the hash entries `prevLength < k <= newLength` migrate into the array (L61-L103, L396-L443). This is simpler than Lua's `computesizes` rehash and gives O(1) amortised appends.
4. **Tombstone-nil hash entries.** Assigning nil to an existing hash key keeps the entry with a nil value and bumps `_nilCount` (`Insert`, L188-L235). `next` therefore stays valid while a loop assigns nil, as Lua requires. **Defect to avoid**: entries are never compacted. `Resize` copies nil entries too (L293-L318), and `Remove` is only called when keys migrate to the array part (`LuaTable.cs` L440). A table used as a set or queue with ever-new keys grows without bound [C: no other `Remove` or `NilCount` consumer in `src/Lua`]. MoonSharp's version must purge nil entries on resize (allowed between traversals; Lua itself only guarantees `next` across nil assignment, not across insertion).
5. **Zero-alloc metamethod `__index` call.** When `__index` is a Lua closure, the VM pushes `(table, key)`, pushes a frame and restarts the loop; the result is copied back by `PopFromBuffer` according to the caller opcode (L1999-L2064, L93-L195). MoonSharp already returns an entry point for Lua callees, so the matching change is making `Internal_InvokeBinaryMetaMethod` and the index path frame-based without allocation.
6. **`LinkedPool<T>`**: an intrusive, `Interlocked`-gated free list capped at 64 entries [C] [LC/src/Lua/Internal/Pool.cs#L11-L67](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/Pool.cs#L11-L67). Safe, AOT-friendly, no `ConcurrentBag`. It is used for `VirtualMachineExecutionContext`, `ThreadCoreData` (stack + frame array per coroutine, so coroutine creation reuses buffers) and the async state-machine boxes.
7. **Stack-overflow guard.** `RuntimeHelpers.TryEnsureSufficientExecutionStack()` before every delegate call and in the parser, plus `MaxCallDepth` [C] [LC/src/Lua/LuaFunction.cs#L20-L30](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaFunction.cs#L20-L30); commit [3012ad64](https://github.com/nuskey8/Lua-CSharp/commit/3012ad64e40194a103bb87d9e9c9571f5c5149ca). The API exists in netstandard2.0, so MoonSharp can use it directly (`RuntimeHelpers.EnsureSufficientExecutionStack` exists on net45 too).
8. **The per-instruction hook check costs one decrement.** When no count hook is set, `HookCount` is 0, so `--hookCount` goes negative and never reaches 0 again in practice. Inside a hook, the refs point at static dummy fields (L396-L401, L421-L426).
9. **Instruction decode through a ref plus `Unsafe.Add`, no bounds check** (L391, L421). The safe equivalent is `var code = proto.Code;` (an array) and `code[pc]`. See the unsafe inventory for its cost.

## 5. CLR interop: `[LuaObject]` generator versus MoonSharp reflection

What the generator does [C]:
- Requires `[LuaObject]` on a **partial, non-nested** class/struct/record that the user owns (diagnostics `MustBePartial` and `NestedNotAllowed`) [LC/src/Lua.SourceGenerator/LuaObjectGenerator.Emit.cs#L104-L131](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua.SourceGenerator/LuaObjectGenerator.Emit.cs#L104-L131). Members are exposed with `[LuaMember]` and metamethods with `[LuaMetamethod]` ([Attributes.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua.Annotations/Attributes.cs)).
- Member types must convert to `LuaValue`, be `ILuaUserData` or be another `[LuaObject]`; otherwise a compile error is reported (`InvalidPropertyType`, `InvalidReturnType`, `InvalidParameterType`) (L300-L360).
- The emitted `__index` is a **linear chain** of `if (stringKey == "Name") return ...` comparisons (L619-L652). The cost is O(members) string compares per access. A C# `switch` on the string (which Roslyn compiles to a length/char-based jump) or a precomputed `Dictionary<string,int>` would be O(1).
- Methods become `static readonly LuaFunction` fields and can be `async` (L1053-L1076).
- The type gets `implicit operator LuaValue`, which wraps it as userdata (L249-L255).

What it **cannot** do, and MoonSharp can:
- Expose types you do not own: `UnityEngine.Vector3`, `GameObject`, BCL types. Lua-CSharp users must write wrappers; issues [#145](https://github.com/nuskey8/Lua-CSharp/issues/145) and [#212](https://github.com/nuskey8/Lua-CSharp/issues/212) are about exactly this friction [S].
- Overload resolution, extension methods, generic methods, events/delegates, indexers on arbitrary types, `IEnumerable` iteration, automatic `List`/`Dictionary` <-> table conversion, enum registration, and registering a whole assembly at runtime.
- Structs are boxed as userdata. Issue [#194](https://github.com/nuskey8/Lua-CSharp/issues/194) asked for an `ILuaValue` to avoid boxing `Vector3`; it was closed "not planned" because the VM stores `LuaValue` and would box somewhere else anyway [S].

Mapping for MoonSharp: keep the reflection descriptors as the default. Add an **optional** Roslyn incremental generator that emits the same `IUserDataDescriptor` implementations Hardwire produces, but at compile time, with `switch`-based member lookup. Hardwire users get an automatic path, and IL2CPP keeps working because no runtime codegen is involved (idea 9).

## 6. Pooling, ArrayPool and GC behaviour

- `ArrayPool<char>.Shared` and `PooledArray`/`PooledList` (ArrayPool-backed, `IDisposable`) for loading, the string library and tracebacks [C] (`LuaState.cs` L625-L627, L709-L720; [LC/src/Lua/Internal/PooledList.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/PooledList.cs)).
- `ValueStringBuilder` (BCL-derived, `stackalloc` initial buffer) for `string.format` and `os.date` [C].
- `stackalloc` small buffers in tracebacks, the scanner and number formatting [C].
- Steady-state Lua execution allocates only for real Lua objects (tables, closures, strings, upvalues, coroutines). GC pressure is therefore proportional to program objects, not to instructions executed. MoonSharp today allocates per instruction (results, local reads, frames, argument lists).

## 9. What not to port

- **ValueTask-everywhere.** It costs a state machine and builder per async path; it caused #126, #327 and the #338 hook overhead; it needs `System.Threading.Tasks.Extensions` on netstandard2.0, which net45 does not support; and it changes every host signature. MoonSharp's synchronous design, with per-coroutine `Processor` and yield-by-return, is better for Unity frame loops. If async hosts are wanted, add an opt-in `CallbackFunction` that returns a "pending" token and resumes through MoonSharp's existing continuation/yield machinery.
- **Unsafe dispatch tricks.** The gain is small (section 7) and they turn bugs into memory corruption.
- **Never-compacted tombstone dictionary.** Copy the idea, not the leak.
- **If-chain member lookup** in generated interop code.

## 10. Prioritised ideas for MoonSharp

Expected impacts refer to the measured MoonSharp numbers (ns/iter, .NET 8): empty_loop 65, function_call 376, method_call 705, table_array_insert 1277, table_array_read 447, table_hash_set_get 757, string_format 4421, int_math 261, fib(12) 188 us, coroutine_switch 899, closure_create_call 662. All estimates are [U].

### P0-a: Explicit open/closed upvalues (prerequisite)
- Mechanism: a closure captures `Upvalue` objects that point at (value-stack array, absolute index) while the frame is alive. On `Ret`, and on block exit for loop-local captured variables (MoonSharp's `Exit`/`Clean` ops), open upvalues at or above the frame base are closed by copying the value in. Locals stop being shared `DynValue` cells.
- MoonSharp mapping: `Execution/VM/Processor/Processor_InstructionLoop.cs` (`ExecClosure`, `GetUpvalueSymbol`, `ExecStoreUpv`, the `Upvalue` op, `ExecRet`, block clean-up ops), `DataTypes/Closure.cs` / `Execution/ClosureContext.cs` (hold `Upvalue[]` instead of `DynValue[]`), `Processor_Scope.cs` (`AssignLocal`, `GetGenericSymbol`), and the debugger (`Processor_Debugger.cs`) local/upvalue views. The compiler already knows which locals are captured (`SymbolRef` types).
- Sources: [UpValue.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/UpValue.cs#L5-L76), [LuaState.GetOrAddUpValue/CloseUpValues](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaState.cs#L724-L751), [LuaClosure ctor](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaClosure.cs#L11-L44).
- Impact: removes the `AsReadOnly()` clone on every local read and the per-local cell. Alone, a 1.3-2x gain on loops that read locals; it also unlocks P0-b.
- Risk: loop-scoped captures (each iteration needs a fresh upvalue, which Lua 5.2 semantics require) and coroutines (an upvalue references its owning `Processor`'s stack). Covered by the closure tests in MoonSharp's test suite and Lua's `closure.lua`.

### P0-b: Internal struct value on the VM stack, locals and tables (keep public `DynValue`)
- Mechanism: an internal `readonly struct Value { object _o; double _n; DataType _t; }` (24 B), or a 16-byte variant where the tag lives in `_o` as sentinel objects. The value stack, frame registers, `Table` storage and closure upvalues hold `Value`. `DynValue` stays the public class and is created only at API boundaries (`Table.Get`, callbacks, `Script.Call` results), with cached instances for nil/true/false and small integers.
- MoonSharp mapping: new `DataTypes/Value.cs`; `DataStructs/FastStack.cs` becomes `FastStack<Value>` with slot clearing on pop; arithmetic, compare, concat and len handlers in `Processor_InstructionLoop.cs`; `Table.cs` storage; boundary conversions in `CallbackArguments`, `ScriptExecutionContext` and `Interop/Converters`.
- Sources: [LuaValue.cs#L23-L37](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaValue.cs#L23-L37), [VM arithmetic L610-L719](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L610-L719).
- Impact: int_math, empty_loop and fib: 3-6x, removing ~230 B/iter; the GC drops out of numeric code.
- Effort: large. Public API compatibility is preserved by the boundary conversion. Allocations shift to the boundaries, so they must stay cheap (cached DynValues).
- Risk: identity semantics. Code that relies on `DynValue` reference identity, on readonly flags or on `Assign` mutating a value seen elsewhere must be audited.

### P0-c: Struct frames, no per-call heap
- Mechanism: `CallStackItem` becomes a struct in a growable array accessed by ref. Locals live on the value stack at `BasePointer` (a register window) instead of `new DynValue[NumVal]`. Rarely used fields (`ErrorHandler`, `Continuation`, `ErrorHandlerBeforeUnwind`, `Debug_Symbols`) move to a side object allocated only when used.
- MoonSharp mapping: `Execution/VM/CallStackItem.cs`, `DataStructs/FastStack.cs` (add `ref T PeekRef()`), `Internal_ExecCall`, `ExecBeginFn`, `ExecRet`, `PerformTCO`, `Processor_Debugger.cs` (call-stack views), coroutine stack copying.
- Sources: [CallStackFrame.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/CallStackFrame.cs#L5-L18), [LuaState.PushCallStackFrame](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaState.cs#L329-L341), [VM Call L1421-L1527](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L1421-L1527).
- Impact: function_call, method_call, fib and closure_create_call: 2-4x on the call portion. Effort: medium-large (needs P0-a). Risk: the debugger and error handlers read frames; keep the public `WatchItem` call stack built on demand.

### P1-a: Table array part + flat struct hash with tombstones and compaction
- Mechanism: a `Value[]` array part (1..n) with Lua-CSharp's growth and migration rule and a known-prefix length cache; a single `ValueDictionary` (open hashing over struct entries) for all other keys instead of `LinkedList` + 3 dictionaries. Insertion order (which MoonSharp's `Pairs` currently follows) becomes array part, then hash slot order. Nil assignment leaves a tombstone so `next` stays valid; tombstones are purged on resize.
- MoonSharp mapping: `DataTypes/Table.cs`, `DataStructs/LinkedListIndex.cs` (removed), `TablePair.cs` (kept for the public API), `CoreLib/TableModule.cs` (insert/remove/sort/unpack fast paths on the array), `Length`.
- Sources: [LuaTable.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaTable.cs#L35-L443), [LuaValueDictionary.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/LuaValueDictionary.cs#L102-L457), commit [606696b3](https://github.com/nuskey8/Lua-CSharp/commit/606696b3c0b41b72f52f75eb75bc2eb08e8be1d3).
- Impact: table_array_insert 10-30x, table_array_read 5-15x, table_hash_set_get 2-4x. Effort: medium (works even before P0-b using `DynValue` slots; better after it).
- Compatibility: `pairs` order changes (Lua does not specify order, but some MoonSharp users rely on insertion order). This is a behaviour change to document; a `ScriptOptions` switch for ordered tables is possible but costly.

### P1-b: Zero-copy CLR callback convention for the standard library
- Mechanism: an internal `delegate int FastCallback(ref CallFrameArgs a)` that sees arguments as (stack, base, count) and writes results at the stack top, returning a count. The standard library modules move to it; public `CallbackFunction` and `CallbackArguments` remain as an adapter.
- MoonSharp mapping: `DataTypes/CallbackFunction.cs` (add a fast field), `Internal_ExecCall` CLR branch, `CoreLib/*Module.cs` (math, string, table first), `Interop/StandardDescriptors/...` (later, for reflection method calls without allocating `object[]` per call).
- Sources: [LuaFunctionExecutionContext.cs#L8-L196](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaFunctionExecutionContext.cs#L8-L196), [VM FuncCall L1482-L1526](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L1482-L1526).
- Impact: string_format 2-4x (alongside a `StringBuilder` cache), method_call 1.5-2x, any stdlib-heavy code. Effort: medium. Risk: low; the public API is unchanged.

### P1-c: Cheap fixes available now (no architecture change)
- `ExecClosure`: replace LINQ `Select(...).ToList()` with a loop into a pre-sized array ([MS/...#L414-L420](https://github.com/emindeniz99/moonsharp/blob/fbd03678d5c0f731d731d099211c7f4a3a1ae8b7/src/MoonSharp.Interpreter/Execution/VM/Processor/Processor_InstructionLoop.cs#L414-L420)). Impact: closure_create_call 1.2-1.5x.
- Arithmetic fast path: `if (l.Type == DataType.Number && r.Type == DataType.Number)` before `ToScalar`/`CastToNumber` (which returns `double?`). Impact: int_math 1.1-1.3x.
- `CreateArgsListForFunctionCall`: share a static empty array instead of `new DynValue[0]`.
- `Instruction[]` snapshot of `List<Instruction>` for dispatch, cached per `Processing_Loop` entry and refreshed when a chunk is loaded.
- Effort: small. Risk: low.

### P2-a: Fused or specialised opcodes (stack-machine "superinstructions")
- Mechanism: the compiler emits `AddLL`/`AddLK` (local+local or local+constant to stack), `StoreLclFromAdd`, `IndexLK` (local table with constant string key), `IncrLcl`. This approximates the register VM's RK operands without rewriting the compiler. Lua-CSharp's RK decode (`RKB`/`RKC`) shows the operand forms worth covering.
- MoonSharp mapping: `Execution/VM/OpCode.cs`, `Execution/VM/ByteCode.cs` (emitters), `Tree/Expressions/BinaryOperatorExpression.cs`, `IndexExpression.cs`, `Tree/Statements/AssignmentStatement.cs`, the dispatch loop, binary dump (bump the dump version).
- Impact: 1.3-2x on top of P0 for arithmetic/index-heavy loops. Effort: medium. Risk: debugger stepping granularity (keep the source refs).
- Alternative, for the owner to decide: transplant a register VM. The go-lua / Lua-CSharp compiler is MIT, but it would replace MoonSharp's AST compiler, binary dump and debugger source mapping. That is large; see section 11.

### P2-b: One-counter hook/budget check
- Fold `DebuggerAttached` and `AutoYieldCounter` into one `long budget` decremented per instruction (or per backward jump and call). Slow path when it reaches 0; debugger attach sets budget to 1. Sources: [VM L396-L426](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Runtime/LuaVirtualMachine.cs#L396-L426); issue #338.
- MoonSharp mapping: `Processing_Loop` head, `Processor_Debugger.cs`, `AutoYieldCounter`. Impact: empty_loop ~1.1-1.2x. Effort: small.

### P2-c: Pools for per-call helpers
- `LinkedPool<T>`-style intrusive pools for `ScriptExecutionContext`, `CallbackArguments`, per-coroutine `Processor` stacks (MoonSharp already has `Coroutine_Recycle`), and `StringBuilder` for `string.format`/concat. Source: [Pool.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/Pool.cs#L11-L67). Impact: coroutine_switch 1.2-1.5x, string_format 1.2x. Effort: small. Risk: use after return; pool only objects whose lifetime ends inside the VM.

### P3-a: Compile-time interop generator (optional) and switch-based member lookup
- A Roslyn incremental generator that emits Hardwire-equivalent `IUserDataDescriptor` classes for `[MoonSharpUserData]` types (and, through an assembly attribute, for third-party types the user lists). Member dispatch uses a C# `switch` on the name, or a frozen dictionary of member index to delegate. Reflection remains the fallback.
- MoonSharp mapping: new `src/MoonSharp.SourceGenerator`, reusing `Interop/StandardDescriptors/HardwiredDescriptors/*` base classes; `UserData.RegisterType` picks up the generated descriptor.
- Sources: [LuaObjectGenerator.Emit.cs](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua.SourceGenerator/LuaObjectGenerator.Emit.cs#L600-L700) (and its O(n) if-chain to avoid).
- Impact: method_call / property access on userdata 2-5x under IL2CPP, where MoonSharp cannot compile expression trees and falls back to reflection `Invoke`. Effort: large. Compatibility: additive; Unity 2021.3 supports Roslyn source generators (DLL marked `RoslynAnalyzer`).

### P3-b: Variable names in runtime errors
- Lua-CSharp ports `ldebug.c getobjname` over bytecode. MoonSharp's stack machine cannot recover names the same way. Instead, record at compile time a name hint on the instructions that can fail (`Index`, `Call`, arithmetic operands) and format "attempt to call a nil value (global 'foo')". `Instruction.Name` already exists for calls.
- Sources: [LuaDebug.cs#L325-L540](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Internal/LuaDebug.cs#L325-L540), [Exceptions.cs#L250-L310](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/Exceptions.cs#L250-L310).
- Impact: none on speed; better diagnostics. Compatibility: error message text changes, so tests that match messages need updating; worth a `ScriptOptions` flag only if users parse messages.

### P3-c: Native stack-overflow guard
- `RuntimeHelpers.EnsureSufficientExecutionStack()` before CLR callback invocation, before metamethod re-entry into `Processing_Loop`, and in the parser's recursive descent, turning a process crash into a `ScriptRuntimeException`. Source: [LuaFunction.cs#L20-L30](https://github.com/nuskey8/Lua-CSharp/blob/a8d84c7c5e858a6118e2a9747f08856f5224793a/src/Lua/LuaFunction.cs#L20-L30). Effort: small. Risk: none known (IL2CPP implements it).

## 11. Decision: (a) base a new engine on Lua-CSharp, or (b) port its techniques into MoonSharp?

### (a) Fork Lua-CSharp and remove its unsafe code
**What we would keep:**
- A register VM that is already 5-10x faster than MoonSharp on most workloads [U, consistent with #156 and the architecture].
- Struct values, zero-allocation calls, and the table array part.
- Official Lua 5.2 test-suite conformance.
- Lua-exact error messages and a `debug` library with hooks.
- MIT licence.
- Unsafe removal is cheap: under ~10% of throughput, and mostly mechanical (section 7).

**What we would lose or have to rebuild:**
1. **MoonSharp's reflection interop**: `UserData.RegisterType`, overloads, extension methods, events, generic conversion, `IEnumerable`, enums, and the standard descriptors. This is MoonSharp's main reason to exist, especially for Unity types the user does not own. It would have to be rewritten on top of `ILuaUserData`/`LuaFunction`.
2. **Hardwire.**
3. **The debugger** (`IDebugger`, VS Code / remote).
4. **Synchronous API and coroutine model**: Lua-CSharp is async-first, with the problems in #126, #327 and #338.
5. **netstandard2.0 / net45 reach**: Lua-CSharp targets netstandard2.1+ and relies on `Unsafe` and Span packages (#337).
6. **MoonSharp's public API** (`Script`, `DynValue`, `Table`, `Closure`, `ScriptOptions`, `CoreModules` sandbox presets, the JSON module, `DynamicExpression`, `string.dump`-style binary chunks, which Lua-CSharp's harness notes are unsupported for `string.dump`).
7. **MoonSharp's UPM package and existing users.**

**Verdict:** this is a new product ("MoonSharp-NG" in name only). Every MoonSharp user would migrate.

### (b) Port the techniques into MoonSharp
**What we would keep:** all of the above (public API, interop, Hardwire, debugger, sync coroutines, netstandard2.0, UPM, error formats).

**What it costs:** the core rewrite (P0-a, P0-b, P0-c, P1-a) touches the processor, closures, tables and the debugger. It is large but incremental, and each step is measurable and testable on its own.

**Where it lands:** a stack machine with struct values, struct frames, superinstructions and an array-part table should reach roughly 2-4x of native Lua on loops and calls [U], against 10-20x today. That is somewhat behind Lua-CSharp's register VM, but it keeps everything users depend on.

### Recommendation: (b), staged, with an explicit checkpoint
1. P1-c quick fixes and P3-c (days). Benchmark: closure_create_call, int_math.
2. P0-a upvalues, then P0-c frames, then P0-b struct values, each behind the full MoonSharp test suite plus Lua 5.2 conformance files. Benchmark after each step.
3. P1-a tables and P1-b the fast callback convention.
4. P2-a superinstructions and P2-b the budget counter.

**Checkpoint for the owner** after step 2: if loops and calls are still more than 4x native, decide whether to replace MoonSharp's compiler and VM core with a register VM. The compiler would be adapted from go-lua / Lua-CSharp under MIT with attribution, sitting behind MoonSharp's unchanged public API, interop and debugger. In effect that is path (a) without losing MoonSharp's shell. It is a breaking change for binary dumps and debugger internals only, and it should be the owner's call per the project rule on legacy-compatibility costs.

Reasons for preferring (b):
- MoonSharp's differentiator is its interop and its debugger, and those are exactly what Lua-CSharp lacks.
- Lua-CSharp's performance comes from techniques (struct values, register windows, zero-copy calls, array part) that are safe C# and portable.
- Its unsafe code buys little.
- Its async core is the part we would most want to remove.
