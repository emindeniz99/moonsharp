## 4. Measurements made for this report

Upstream `fbd0367` interpreter compiled from source into the measuring program ([src/DevTools/Research/UnityEnhancedPoc](../../src/DevTools/Research/UnityEnhancedPoc/README.md), which has the commands; net8.0, Release; a `global using` alias resolves the `ReferenceEqualityComparer` ambiguity on net5+, the same thing the fork fixes in `EventMemberDescriptor.cs`). 4-core x64 VM, .NET 8.0.33, best of 7 runs of 1,000,000 iterations each, `GC.GetAllocatedBytesForCurrentThread`. Two full runs; the table shows run 2 (run 1 within ±8%).

**Experiment A: "immutable values + cells only for captured locals"**, a 30-line proof of concept of idea 1 applied to a copy of upstream `fbd0367` (not to our repo; `poc.patch` in the same folder): local reads push the slot's value without cloning unless the slot is a cell; `AssignLocal` replaces the slot reference unless it is a cell; capturing a local in a closure turns its slot into a cell; `ExecArgs` stops cloning; `ExecIncr` allocates a fresh number. Upvalue reads still clone (the full design removes that too).

| Workload | upstream ns/iter | upstream B/iter | PoC ns/iter | PoC B/iter |
|---|---|---|---|---|
| `s = s + i % 7` loop | 189 | 240 | 163 | 144 (−40%) |
| `s = a` loop (local read) | 87 | 96 | 76 | 48 (−50%) |
| closure incrementing an upvalue | 253 | 360 | 224 | 312 (−13%) |

## 5. Ideas for MoonSharp, ranked

### Idea 1 (high): immutable value semantics in the VM, with explicit upvalue cells

- **What the fork shows:** almost every DynValue clone in the VM exists only because locals are mutable boxes that get `Assign`ed. Make the VM never mutate a DynValue it did not just create, and the clones on local read, upvalue read, argument binding and field read all go away.
- **MoonSharp mapping:**
  - New `internal sealed class UpvalueCell { internal DynValue Value; }` (one field, 24 B).
  - `ClosureContext : List<DynValue>` → array of `UpvalueCell` (`Execution/Scopes/ClosureContext.cs`). `Closure.GetUpvalue`, `DebugModule.getupvalue/setupvalue/upvalueid/upvaluejoin` use the cell; `upvalueid` can use a lazily assigned ID on the cell.
  - `CallStackItem.LocalScope`: either `object[]` holding a DynValue or an `UpvalueCell` (runtime check, as in Experiment A), or better, the compiler marks captured locals (`BuildTimeScope`/`BuildTimeScopeFrame` already resolve upvalues at compile time in `Tree/` and `Execution/Scopes/`) and emits distinct opcodes (`Local`/`LocalCell`, `StoreLcl`/`StoreLclCell`), so the hot path has no type check. Captured locals get their cell at `ExecBeginFn`/block entry; `ClearBlockData` resets them so per-iteration captures still work.
  - `Processor_InstructionLoop.cs`: `OpCode.Local`, `OpCode.Upvalue`, `AssignLocal`, `ExecStoreUpv`, `GetUpvalueSymbol`, `ExecClosure`, `ExecArgs`, `ExecIncr`, `ExecIndex` (drop `AsReadOnly`). `Processor_Scope.cs` (`GetGenericSymbol`/`AssignGenericSymbol`) and `Processor_Debugger.cs` (locals/watches) follow.
  - Public DynValue API stays: `Assign`, `Clone`, `AsReadOnly`, `ReadOnly` remain for hosts (marked `[Obsolete]` later after an owner decision); the VM simply stops relying on them. Values the VM hands to callbacks should be treated as immutable; document that `Assign` on a value received from Lua no longer changes the Lua variable (it never reliably did).
- **Impact:** measured −33% to −50% bytes and 12–18% time on loops and calls with a partial PoC (§4). Full version also removes the upvalue-read clone (closure_create_call, method_call, coroutine workloads) and enables idea 3. Expect `empty_loop`, `int_math`, `function_call`, `fib` to improve most.
- **Effort:** medium (compiler opcode split + debugger plumbing + dump format if new opcodes; bump the dump version).
- **Risk:** aliasing bugs if any path still mutates a shared value. Grep-able: `Assign(`, `AssignNumber(`, `m_Number =`, `m_Object =`. Needs the full test suite + new aliasing regression tests (the eight cases in §4 are a starting set).
- **Compatibility:** no unsafe, IL2CPP-safe, netstandard2.0-safe. Binary dumps change if new opcodes are added.

### Idea 2 (medium): shrink DynValue to 40 B without breaking the API

- Remove `m_HashCode` (recompute; string hashing in `Table` goes through `m_StringMap` keyed by `string`, so only `m_ValueMap` keys pay), and stop assigning `m_RefID` in the field initialiser. Keep `ReferenceID` as a lazily assigned value stored outside the object, e.g. a `ConditionalWeakTable<DynValue, StrongBox<int>>` only touched by the debugger/`upvalueid`/`ToString` of coroutines. Keep `DataType : int`; `double + object + int + bool` already packs into 24 B.
- **Files:** `DataTypes/DynValue.cs`, `CoreLib/DebugModule.cs` (`upvalueid` moves to the cell from idea 1), `Execution/VM/Processor/Processor_Debugger.cs`, `MoonSharp.VsCodeDebugger/DebuggerLogic/VariableInspector.cs`.
- **Impact:** −17% bytes per remaining DynValue allocation; removes a non-atomic static write per allocation (shared cache line across threads). Benefits every workload that allocates numbers/strings.
- **Effort:** small. **Risk:** low; `ReferenceID` values become sparse/lazy (documented as debug-only already).

### Idea 3 (medium): constant singletons, plus a small-integer cache

- VM-internal: push `DynValue.True/False` instead of `NewBoolean` (`ExecNot`, `ExecCNot`, `ToBool`, `ExecEq`, comparisons). Safe **today**, because `True`/`False` are readonly and no VM path assigns into a comparison result.
- After idea 1: `NewNumber` returns cached instances for integral values in, say, −256..1023 (Java `Integer` cache style), used by arithmetic, `#`, `ipairs` indices and `for` counters. The fork caches only 0 and 1.
- Public factories: keep `NewBoolean`/`NewNumber` returning fresh writable values (their documented contract) until the owner decides; add internal `FromBool`/`FromNumber` used by the VM and CoreLib.
- **Impact:** removes one allocation per comparison/`not` and many per integer loop (`table_array_read/insert` index values, `int_math`). **Effort:** small. **Risk:** low with the public/internal split.

### Idea 4 (medium, startup): cache module registration, write `require` in C# properly

- `Modules/ModuleRegister.cs`: a static, lock-protected (or `ConcurrentDictionary`) cache `Type → (name, Func<ScriptExecutionContext, CallbackArguments, DynValue>)[]`, constants, `MoonSharpInit` MethodInfo, and string-field Lua sources. Per `Script`, only create `CallbackFunction`/`DynValue` objects and `Table.Set`. Keep `RegisterScriptField` for user modules that define Lua-source methods.
- `CoreLib/LoadModule.cs`: replace the Lua `require` string with a C# callback that returns `DynValue.NewTailCallReq` to the loaded chunk with a `Continuation` (same mechanism as `pcall`, `ErrorHandlingModule.cs` line 59, and `tostring`, `BasicModule.cs` line 136) that stores `package.loaded[name] = (res is nil or void) ? true : res`. This stays yieldable and keeps Lua semantics, fixing both bugs of the fork's version.
- **Impact:** measured registration share ≈ 1.2 ms of 1.4 ms default `new Script()` upstream (§4 B). Expect our current 0.64 ms to drop well under 0.2 ms; matters for Unity "one Script per entity" and for the web/worker hosts.
- **Effort:** small–medium. **Risk:** low; `require` changes from Lua function to CLR function (visible via `debug.getinfo(require).what`, `string.dump(require)` errors). Document in the migration notes.

### Idea 5 (medium, interop): versioned cache for resolved type descriptors

- `Interop/UserDataRegistries/TypeDescriptorRegistry.cs`: add `Dictionary<Type, IUserDataDescriptor> s_ResolvedCache` and an `int s_RegistryVersion` bumped by every `RegisterType`/`UnregisterType`/policy change. `GetDescriptorForType(type, searchInterfaces=true)` first checks the cache (with the version), otherwise computes exactly as today and stores the result, including `null` (negative caching) and the composite. Do **not** call `PerformRegistration` (the fork's approach changes `IsTypeRegistered` and history).
- **Impact:** every `UserData.Create(obj)` / CLR→Lua conversion of an object whose concrete type is not registered but a base or interface is (common: `List<T>` via `IList`, game objects via base classes, enumerators) stops allocating the `GetInterfaces()` array, a `List`, and a new `CompositeUserDataDescriptor`. Should be measured on `method_call` style benchmarks that return such objects; expect a large relative win on that path, none on registered-type paths.
- **Effort:** small. **Risk:** cache invalidation; covered by tests that register a base/interface after first use.

### Idea 6 (medium, interop): memoize fuzzy name resolution instead of removing it

- `Interop/BasicDescriptors/DispatchingUserDataDescriptor.cs` (`Index`, `SetIndex`) and `PropertyTableAssigner.cs`: per-descriptor `Dictionary<string, string>` from requested name → matched member name (or a sentinel for "no match"), keyed together with `Script.GlobalOptions.FuzzySymbolMatching` and the extension-method version. First miss pays the `UpperFirstLetter`/`Camelify` cost; later accesses do one dictionary lookup. Same for `TryIndexOnExtMethod`.
- **Impact:** Lua code that uses `obj.someMethod` for C# `SomeMethod` (the documented MoonSharp style) currently allocates up to three strings per access; also negative lookups (`if obj.optional then`) pay the full fuzzy chain and extension-method search every time. **Effort:** small. **Risk:** low; bounded by the number of distinct names used.

### Idea 7 (low): empty fast path for CustomConverters

- `Interop/CustomConvertersCollection.cs`: maintain `internal bool HasScriptToClr`/`HasClrToScript` (or a count) updated by the setters and `Clear`; the four call sites in `ClrToScriptConversions`/`ScriptToClrConversions` check the flag first.
- **Impact:** one dictionary lookup saved per converted argument and return value when no converters are registered (the usual case); small but on every interop call. **Effort:** small. **Risk:** none; public API unchanged.

### Idea 8 (low): per-Script literal string sharing (the safe part of P6)

- Literals are already a single readonly DynValue per `LiteralExpression`. If profiling shows repeated runtime creation of the same short strings (table keys from `string.format`, `tostring` of small ints), add a bounded, per-`Script` cache for `tostring` of small integers only. Do **not** intern arbitrary runtime strings process-wide.
- **Impact:** small; measure first.

### Not adopted (with reason)

- Global static string table (leak + thread safety), `DynValueAccessor` delegates (more allocations than upstream), unsealing DynValue, fixed small stacks / TCO threshold change (superseded), removal of coroutine recycling, CustomConverters, fuzzy matching, `debug.upvalueid`, `AutoDescribingUserDataDescriptor` visibility, and every reverted fix in §3.3.
- Returning internal lists from `MultiDictionary.Find` outside locks.
- Field reordering (no effect on CoreCLR/Mono auto layout).

## 6. Answers to the brief's specific questions

- **DynValue changes:** immutability (worth it, needs cells), size 48 → 40 B by removing ID/hash/readonly (worth it, keep API via lazy ID), constant singletons (worth it), global interning (reject), unsealed + public field (reject).
- **Stack sizing:** injectable fixed sizes, superseded by our growable stacks.
- **Descriptor caching:** idea valid; implement as a versioned side cache.
- **require in C#:** valid; the fork's implementation is not yieldable and mis-handles a void module result.
- **String handling:** only the global intern table; reject.
- **Table changes:** only `AggressiveInlining` and `?.`; no structural change (no array part). Nothing to take.
- **Pooling:** none added; coroutine recycling (a pool) was removed.
- **Interop:** fuzzy matching and custom converters removed (memoize / fast-path instead), numeric conversion overflow checks reverted (keep upstream), LINQ removed from registration (minor).
- **Coroutine recycling and call-site source fix:** both confirmed removed/reverted; keep upstream behaviour.
